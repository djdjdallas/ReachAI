# Clinchd / ReachAI — App Audit (2026-06-26)

## Summary

The app is broadly healthy: no P0/P1 defects surfaced, and the core flows (webhook ingestion, AI reply pipeline, billing, OAuth token storage) are mostly sound and already encrypted at rest. The dominant themes are (1) **rate-limit / send governance gaps** that risk Meta account restrictions, (2) **silent-failure UX** where mutations skip error checks, and (3) **process debt** — zero tests, a red lint baseline, and timestamp/util drift the recent UTC work was meant to end. 34 findings were confirmed (13 P2, 21 P3) after adversarial verification; **2 candidate findings were refuted** during verification (the classifier prompt-cache claim was partially refuted and downgraded — only the `dm-intent` path misses the 4096-token cache, not `classifier.js`; and the lint "ordering bug / can break build" sub-claims were refuted — `fetchData` is a hoisted declaration and Next 16 runs no build-time lint).

**Top 3 risks**
1. **Uncapped/unmetered Meta sends** — the drip processor and the comment-to-DM path send before (or without) reserving a 200/hr slot, a pattern that already earned the founder account a 30-day restriction (F3, F6).
2. **Silent revenue loss** — a Stripe price-ID rotation makes `getPlanFromPriceId()` default to `"base"`, downgrading every paying Unlimited customer and killing voice/drip/comment features on their next `subscription.updated` (F8).
3. **Anon-callable RLS-bypass RPCs** — `increment_dm_count`, `check_and_record_outbound`, `check_ai_rate`, and the `purge_*` functions are SECURITY DEFINER with no REVOKE, exposing a cross-tenant DoS via the public anon key (F9). Plus the fail-open cron auth (F12) if `CRON_SECRET` is ever unset.

**Top 3 feature bets**
1. **Unified outbound send governor** — one helper wrapping `check_and_record_outbound` (+ DM count) called by every Graph-write path; fixes the root cause of F3/F6 across text, voice, and comment surfaces.
2. **Crisis/self-harm hard-pause independent of confidence** — closes F5, the most dangerous trust/liability gap, in ~S effort.
3. **Minimal Vitest + pre-commit harness** — covers webhook HMAC, gate logic, drip conditions, and date parsing; directly addresses F13 and the regression class that drove the recent UTC fix commits.

## Security findings

- **Anon-callable RLS-bypass RPCs (F9, P2).** The older SECURITY DEFINER functions (`increment_dm_count`, `check_and_record_outbound`, `check_ai_rate`, `purge_closed_conversation_data`, `purge_old_comment_data`) carry no GRANT/REVOKE, so Postgres' default EXECUTE-to-PUBLIC exposes them through PostgREST `/rest/v1/rpc/*` to the public anon key. Newer functions (`claim_due_drips`, `increment_voice_send_count`, `match_and_claim_native_send`) correctly grant only to service_role — the gap is an inconsistency, not a design choice. Concrete abuse: `POST /rest/v1/rpc/increment_dm_count` with a victim's UUID inflates `dm_count_this_month` past 1500, silencing that tenant's AI auto-replies (cross-tenant DoS). Tempered only by the victim UUID not being publicly surfaced. The `purge_*` functions are unauthenticated-callable but bounded to already-aged rows. **Verify live grant state with `\df+` / `pg_proc.proacl` — a manual REVOKE could exist outside the migration files.**
- **Cron auth fails open (F12, P2).** If `CRON_SECRET` is ever unset, all three cron handlers accept `Authorization: Bearer undefined`, opening drip email fan-out, Meta token mutation, and quota consumption. `drip/enroll` already fails closed — mirror it everywhere.
- **Stripe webhook → silent downgrade (F8, P2).** Not an auth hole but a billing-integrity risk: a price-ID rotation silently demotes the entire paid tier. Recommend pairing the fix with a Stripe idempotency ledger (feature below).
- **SECURITY DEFINER search_path (F24, P3).** Lint-flagged hardening; low real-world exploitability given schema-qualified bodies and PG15 default CREATE revocation on public.
- **Token-at-rest co-location (F25, P3) + OAuth secrets in URLs (F22, P3) + ENCRYPTION_KEY validation (F23, P3).** Defense-in-depth: tokens are AES-256-GCM encrypted with a server-only key and there is no client-side decrypt path or demonstrated log leak today, so none are live exposures — but each lowers the blast radius of a future mistake. The token-wipe-to-null pattern (F21) is mitigated by provider behavior but worth the one-line guard.
- **No security response headers (F35, P3).** Missing clickjacking/HSTS/referrer hardening on an authenticated, token-bearing dashboard.
